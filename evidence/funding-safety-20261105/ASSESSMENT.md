## Actual invariant and implications

Source: `preseason/allowance/template.ts`, `lab.ts`, `lab.test.ts`. Let B=P+1000. Every spend requires one token-free input of V=N*B, 1<=N<=100, transaction version 2, locktime 0 and exact sequence T (1..65535), plus CSV. N>1 produces precisely V-B back to the identical locking script and P to the fixed beneficiary; N=1 produces only P to that beneficiary. Fee is therefore exactly 1000. The fixed beneficiary is synthetic P2PKH hash `22` repeated 20 bytes, with no ownership evidence or usable key established. Never fund this lab even when its arithmetic passes.

- **Wrong nonmultiple amount, zero, below B, or over 100*B:** no satisfying spend under the current covenant. There is no sweep, admin, donor, beneficiary or timeout override. This is a script restriction, not merely a relay-policy failure. Changing application checks, paying a miner more, or waiting longer cannot repair it.
- **Wrong intended count but valid multiple:** a real distinction. If intended N=3 but V=4*B (within the cap), the covenant permits four payments, not a locked balance. V=2*B permits two. The script encodes an upper limit, not an independent committed initial N. Diagnostics must separately compare observed count against an explicitly reviewed expected count, rather than label every valid multiple “correct”. This is an irrevocable economics mismatch.
- **Top-ups and split funding:** receiving another transfer creates a different outpoint. Amounts sent to the same script/address do not merge. Two malformed coins whose sum equals a valid reserve remain malformed; a good coin does not rescue a bad coin because multiple inputs are forbidden. Multiple good coins create concurrent independent schedules, not one global allowance. Never sum wallet/address balances when classifying funding.
- **Token contamination:** an actual token category or NFT-bearing input violates the covenant even if fungible amount is zero. A later token-free transfer is a separate coin; it does not remove tokens from the original. Synthetic DTOs should reject any supplied token field rather than coercing or stripping it.
- **Dust:** the lab fixes P>=546. At the explicitly declared 1000 sat/kB dust-relay baseline, token-free P2PKH dust threshold is 546 and the 35-byte P2SH32 reserve threshold is 576 (44-byte serialized output +148 assumed input bytes, multiplied by 3). Minimum valid reserve B=1546 already exceeds 576. Exact arithmetic and terminal branch prevent a sub-tranche residual output. Dust received at the contract is also below B, hence unspendable here for the stronger arithmetic reason. Dust standardness is not a BCH consensus floor. A miner accepting a dust funding output would not make its covenant spend valid.
- **Lost or wrong beneficiary key:** permissionless release still works because the covenant requires no beneficiary signature. Each release continues paying the same P2PKH script, where spending does require its key. The donor cannot redirect future payouts or reclaim the reserve. A known backup restoring the same key could restore access, but the contract itself cannot. Do not claim reserve release fails merely because a key is lost; the economic loss occurs at the immutable destination.
- **Fee changes:** the exact fee cannot be raised or lowered in-place. Extra input sponsorship violates one-input shape; reducing reserve/payout or appending change violates exact amounts/count. Current synthetic 1000-sat fee divided by measured bytes is descriptive, not a future relay/mining guarantee. A higher local dust policy may also reject the fixed payout. Such policy refusal can be temporary and is distinct from an impossible script. Do not promise a global unspendability result merely from one policy threshold.
- **Timing:** source-chain heights matter. With parent confirmation height h and exact block sequence T, BCHN's sequence-lock formula is h+T-1 and the spend block must be strictly higher, hence earliest height h+T. Subsequent reserve confirmation restarts the delay. Missed time does not accrue catch-up payments, time is not calendar time, and reorganizations can alter eligibility. Stateless libauth CSV checks sequence/version/flags, not real parent age or unspentness.

## Designs that would change trust or economics (not implemented)

1. Donor refund/timeout branch: creates revocation or eventual forfeiture risk and race conditions; changes the nonrevocable beneficiary promise. Funding-origin authentication and exact refund destination would need design.
2. Beneficiary key rotation or recovery/admin/multisig branch: changes the authority model and introduces alternate spend rights, key availability and compromise risks.
3. Adaptive fee/subsidy inputs or fee reserve: changes accounting, allowed input/output shape, payer consent and possible extraction bounds. A fee cap alone does not prove a safe multi-input covenant.
4. Arbitrary-balance terminal sweep or rounding: changes exact payment/cap/fee economics or leaves locked residue. Silently treating remainder as fee is not recovery.
5. Funding many short-lived smaller valid UTXOs: changes timing/economics because schedules run concurrently and adds funding transactions/costs. It is not equivalent to one N-tranche chain. A future just-in-time donor schedule removes prefunding assurance and adds donor availability/trust.
6. Child-pays-for-parent or direct miner assistance: does not change the parent covenant or make invalid parent scripts valid. Beneficiary spending could theoretically subsidize an ancestor, but needs key/signing, separate spending and verified node/miner/package support. The next reserve is itself CSV-delayed. No current route is verified or authorized, and none should be advertised as guaranteed recovery.

## Recommended bounded implementation and acceptance tests

Pure report API accepting strict decimal integer satoshi strings, existing parameters, explicit expected tranche count and an explicit synthetic single-output description. Keep separate verdicts: format, token exclusion, arithmetic count/remainder, expected-count match, declared dust-policy compatibility, declared fee/byte compatibility, recovery availability. Unsupported fields and numeric coercion fail closed. Do not return “funding safe” or any live/ownership verdict. Report total beneficiary amount N*P and cumulative fixed claim fees N*1000 as economics only; these exclude any initial funding transaction fee and beneficiary later spend fees.

Use per-UTXO semantics. Reject collection aggregation, expected-count omission (or report it explicitly unknown), wrong script/parameters, negative/leading-zero/decimal/exponential/unsafe number amounts, token/NFT presence and above-cap values. Check B-1, B, B+1, 100*B, 100*B+1, 101*B, and valid under/over-intended counts. Distinguish script-invalid from policy-incompatible. Include dust boundary 545/546 and reserve 575/576 in helper policy tests without pretending those tiny reserves are valid covenant deposits. All responses must state no recovery, fixed beneficiary and fee, no live verification and funding prohibited. Keep existing Guard rejection and CLI no-raw-bytes behavior unchanged.

This delivers a concrete safety analysis tool without authorizing funding or silently replacing the contract. Normal supported Invitation execution/follow-up discovery and exact-fee handling remain independent blockers.

Receiving a new output does not execute the recipient's future spend covenant, so local preflight cannot prevent arbitrary third-party deposits.
