## Decisive finding (verified)

A signature-free BCH covenant is not a signature-free XO participation workflow. The tranche release script only supplies the covenant redeem script, but normal XO participation authenticates commits separately:

- [createInvitation](https://gitlab.com/GeneralProtocols/xo/engine/-/blob/18c44c1b0e9254882dbdbbc1e41bd559244bdda4/source/invitation/participation/create.ts#L65): unconditional signInvitationCommitWithSchnorr at 65–72. Optional action/role key generation is additional, not a replacement for the identity signature.
- [appendInvitation/applyInvitationAppend](https://gitlab.com/GeneralProtocols/xo/engine/-/blob/18c44c1b0e9254882dbdbbc1e41bd559244bdda4/source/invitation/participation/apply-append.ts#L98): unconditional new signed commit at 98–105.
- [signInvitation](https://gitlab.com/GeneralProtocols/xo/engine/-/blob/18c44c1b0e9254882dbdbbc1e41bd559244bdda4/source/invitation/generation/unlocking-bytecode.ts#L97): compiles input unlocking data, then calls signed append at 115. No CHECKSIG in the contract does not bypass this append.
- [executeAction](https://gitlab.com/GeneralProtocols/xo/engine/-/blob/18c44c1b0e9254882dbdbbc1e41bd559244bdda4/source/invitation/participation/execute.ts#L198): builds, then signs and stores a created result BEFORE testing broadcastTransaction. false disables broadcast, not identity signing or state mutation (lines 208–215; result signing at 78–84).
- [Official Getting started](https://stack.xo.cash/getting-started.html), freshly read, agrees: a commit is a signed participant addition; executeAction(false) builds and records. Engine.create opens mnemonic-backed state and connects to Electrum. It is not a safe read-only preview entry point.

## Important integration distinctions (verified source; actual lab workflow unverified)

1. Roles: the lab requires one relay participant for continue/final; that role is carried by a signed commit. helpers/roles.ts:23–39 counts commit role and item role tags. Its contract script has no cryptographic spending authority, but its XO participant still has an identity. validation/follow-up-roles.ts allows at most one follow-up role per entity. The lab has global lockingScript.actions rather than lockingScript.roles, so these global actions are distinct from the per-role restriction; absence of a role conflict does not demonstrate discovery.
2. Unlocking: [prepareInputUnlockingCompilation](https://gitlab.com/GeneralProtocols/xo/engine/-/blob/18c44c1b0e9254882dbdbbc1e41bd559244bdda4/source/compilation/generate-unlocking-bytecode.ts#L183) requires tracked, available UTXO state and stored script-hash data at 183–209, even before any key operation. listOwnInputIndexes similarly means tracked and reservable, not cryptographic ownership proof.
3. Follow-up: official docs discover intents from the stored script's lockingScript.actions plus that account's lockingScript.roles[role].actions. The lab includes global tranche actions, but no real stored script/UTXO/next Invitation has exercised discovery. [trackInvitationScriptHashes](https://gitlab.com/GeneralProtocols/xo/engine/-/blob/18c44c1b0e9254882dbdbbc1e41bd559244bdda4/source/invitation/helpers/outputs.ts#L285) stores, subscribes and fetches UTXOs. It is not a pure discovery check.
4. Change: [addChangeToInvitation](https://gitlab.com/GeneralProtocols/xo/engine/-/blob/18c44c1b0e9254882dbdbbc1e41bd559244bdda4/source/invitation/change/add.ts#L201) appends another output and signed commit. executeAction does not call it. The template-writing blog's broad automatic-change language must not override pinned source or getting-started's explicit conditional addChange call. Our exact shape and fixed 1000-satoshi fee require no added change; a candidate must be independently checked for this. Omitting change is compatible with the explicit API, but normal lab Invitation integration is still unproven.
5. inputsMissingSignatures is really a missing-unlocking-bytecode check (requirements/signatures.ts:7–11,28–39). A nonempty redeem-script push can satisfy that field without a BCH transaction signature. That says nothing about Invitation commit authenticity or chain maturity.

For follow-up discovery evidence, additionally request a secret-free existing script-hash record (templateIdentifier, lockingScriptIdentifier, outputIdentifier, roleIdentifier, public variables) and the successor Invitation or original application export showing which intent was selected. Treat all supplied state as untrusted historical evidence, never fresh chain/ownership proof.
