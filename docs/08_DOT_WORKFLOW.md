# 面向 ChatGPT dot 的执行工作流

## 1. 用官方能力设计任务，而不是发明控制语法

OpenAI 当前资料确认：dot 有自己的云端电脑与浏览器，可以协调并行后台工作；特定仓库的 Codex 云任务需要已设置的环境；本地任务需要连接电脑保持在线。新任务有自己的上下文，不自动收到所有聊天历史。任务“运行完成”也不等于目标已经实现。[S23–S25]

由此，本包采用**一个 dot 总负责人、可验收的小任务、持久文件状态、独立验证**。不依赖原稿的 `@dot [Active Codex Task - Branch: ...]` 成为某种官方可执行指令，也不保证任意环境都有某个 `/agents` 命令或相同 Code Review 视图。

Git worktree 是可用时的工程隔离手段，不是 dot 自动提供的永久云能力。若只有一个可写工作区，改为按文件归属或顺序实施；若无 Git 写入权限，仍可在本地准备差异与测试结果，报告具体推送阻塞。

## 2. G0 环境清点

dot 在 `evidence/setup/environment.md` 记录：

| 项目 | 应取得的证据 | 缺失时做什么 |
| --- | --- | --- |
| 仓库 | 实际 repo、HEAD、分支、访问权限 | 未提供旧仓库就不宣称迁移；继续独立新项目准备 |
| 执行环境 | 云电脑/已建Codex环境/连接电脑的实际位置 | 只用实际可调用能力，不等候不存在的后台任务 |
| 终端与依赖 | Node版本、包管理器、lockfile、安装日志 | 先修一个可重现环境；不随意全升级 |
| 浏览器 | 可访问本地或预览站、截图/交互能力 | 本地单测继续；把真实UI测试列为确切缺口 |
| 钱包 | 用户能打开的具体钱包版本和设备 | 先做纯数据验证，不伪造钱包验收 |
| 外部服务 | GitHub、部署服务、RPC、可选模型的真实权限 | 优先读写连接器；需要登录时按平台私密流程 |
| 预算 | 已有额度、拟新增支出、主网测试范围 | 先给可审阅成本和交易清单，不自动开付费服务 |

当前文档并未证明用户有所有这些权限，也未读取私人仓库。相关事实从 UNKNOWN 起步。

## 3. 任务划分与上下文传递

推荐角色是职责分工，可由一个 agent 顺序完成，也可在可用并发数内委派：

- dot / 集成人：范围、官方规则、任务依赖、合并、验收和与用户沟通。
- BCH 编码任务：wallet adapter、链适配器、金额/UTXO与交易构建。
- 产品任务：意图确认、检查报告、收据和开发者入口；只消费已固定接口。
- 独立验证任务：从规范设计负例，审查错误放行、重复付款和实际UI，避免只重复实现者结论。

任务必须携带 `templates/TASK_HANDOFF.md` 的字段。特别写明基线 commit、可修改路径、引用的规格版本、可运行命令、done条件、未确定接口和禁止推断。只发“把Task3做完”不是完整交接。

允许并行：已冻结契约后的 UI 与 guard 实现；官方规则核查与本地编码；文案材料与性能修复。必须顺序：SDK spike→适配器；意图/交易契约→guard；guard→真实签名；签名/广播→收据；主线稳定→XO/跨链。不要让多个任务同时写 package.json、lockfile 和公共类型。

## 4. 持久状态与恢复

| 文件 | 内容 | 更新时间 |
| --- | --- | --- |
| `docs/STATUS.md` | 当前阶段、完成/阻塞、证据、真实设备、未通过项 | 每个实质切片完成或失败后 |
| `docs/DECISIONS.md` | 决策、来源、取舍、允许重开的触发条件 | 范围/API/依赖改变时 |
| `docs/NEXT_ACTION.md` | 下一个可执行动作及依赖 | 暂停、换任务、上下文恢复前 |
| `evidence/dependencies.md` | 精确版本、registry来源、工具版本、lockfile hash | 安装与版本变化时 |
| `evidence/validation/summary.md` | 哪个commit上跑了什么、结果与未测项 | 验证完成后 |
| `evidence/submission/manifest.json` | 交付URL、源码commit、主网txid、规则证据 | 发布/提交流程前 |

OpenAI 的长任务实践强调把规格、计划、执行说明和状态写进持久文件；本包据此设计上述项目流程。[S26] 这里不保证任何一次聊天都完整保存代码、浏览器状态或所有记忆。

恢复时先检查实际 workspace 和 commit，不直接相信上一条“完成”。如果测试证据对应旧 commit，明确哪些修改影响它；只补相关风险的验证，不每次从零全量重跑。

## 5. 编码循环

1. **选择一个可见结果。** 例如“用户可看到被替换的收款脚本并无法进入签名”。
2. **确认依赖与基线。** 读取类型、已有实现和关键测试；记录限制。
3. **实现最小变更。** 无需无关重构；保留公共API一致。
4. **验证风险。** 用一个有效样例和真正改变结果的负例检查，再做涉及此UI的点击验证。
5. **审查实际产物。** 看 diff、构建输出和页面，而非只读 agent 总结。
6. **更新状态并集成。** 已验证的切片进入统一集成分支；剩余风险和下一步写清楚。

不让模型无限添加“安全功能”、告警平台、架构层和测试文件。发现的风险必须联系具体资金错误、用户障碍或比赛资格；纯假想边界可以记录为后续，不拖延交付。

## 6. 权限与人工步骤

已获用户委托的读资料、写代码、局部修复、测试、准备提交文件按正常工作自主推进。用户授权具有持续性，已经明确允许的范围不逐步重复确认。

本任务只是开发文档，**未授权本轮 agent 替用户报名、发消息、支付、申请或公开发布**。未来 dot 收到执行委托后，应依据届时真实授权行动；确需用户确认时，先完成所有准备并交出具体可审核对象。

| 动作 | dot准备工作 | 必要的人或外部条件 |
| --- | --- | --- |
| 参加roll call | 给出准确直播/点名入口、材料和时间 | 用户真实出席；不能自动代替 |
| Telegram确认/导师问题 | 准备短消息草案、核对官方收件渠道 | 明确发信授权或用户亲自发送 |
| 主网实测 | 精确网络、地址、资产、金额、手续费上限、失败恢复计划 | 用户已授权该范围并在钱包签名 |
| 源码公开/部署 | 审阅过的commit、license、secret检查与可用构建 | 依当前用户授权/服务审批，不额外制造流程 |
| 参赛/bounty提交 | 表单草稿、证据、IP条款范围、可访问链接 | 用户对实际条款与提交内容的确认或既有明确授权 |
| XO个人反馈 | 原始日志、时间和重现步骤 | 用户本人真实体验及写作 |
| Team1申请 | 真实成果、预算和里程碑草稿 | 用户确认身份与申请陈述后按授权提交 |

拒绝或连接错误要报出具体动作、实际理由和可继续的工作，不把“系统不允许”当作一切阻塞的笼统解释。不得绕过平台自动审批，也不能以文档里的“全自动”覆盖用户权限。

## 7. 计划与时间触发

开发前期到比赛有时间间隔。dot 可以保存下一阶段计划；若用户希望每天跟踪官方规则或届时开始开发，应实际创建受支持的定时任务，记录时区、结束日、触发内容和通知规则，并返回创建结果。**把日期写进 Markdown 不代表自动化已创建。** 本交接包没有创建任何提醒或持续监控。

建议跟踪点：下一次准备直播前、11月12日前的注册、11月14日开赛前的规则与依赖、11月20日功能冻结、11月21日内部提交。遇到赛事变更只更新已核实事实；未确认消息保留来源和状态。

## 8. 独立审查与验收

审查任务先看实际diff与证据，不先灌输“此前已通过”。审查重点：意图是否独立、是否每个输出均检查、未知状态是否误显成功、签名后能否改变资金字段、是否把真实钱包与mock混称、是否夸大参赛/资助资格。

如用户已有外部监工模型和可用接口，可以在现有授权下把脱敏diff与证据交其复核；不能编造本次已经调用过 Argon/Gemini，也不为了监工去暴露密钥。本包不绑定额外付费模型才能完成。

最终报告固定回答：做了什么、哪个commit、如何启动、哪台设备/钱包实测、哪笔主网交易、有哪些失败恢复证据、规则还有哪些未完成、用户下一步只需做什么。附上具体链接和文件，不只给终端成功截图。
