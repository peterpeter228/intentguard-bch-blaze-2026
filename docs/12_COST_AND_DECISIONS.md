# 时间、成本、商业验证与范围决策

## 1. 不给无依据的获奖概率

目前没有可靠的参赛项目质量分布、最终人数、评委分数或赞助方候选数据，不能给“获奖70%”“保底奖金”之类数字。这个方案能改善的是**资格完整、交付成功、评委理解、技术可信和业务证据**，不是保证结果。

名次奖、多个bounty、共享完赛池与独立grant是不同机制。只比较可单独争取的机会，不把奖金总额当收入预算。PUSD名义计价与实际兑换价值也要区分；本项目没有对PUSD价格、偿付或流动性作保证。[S01/S03/S20]

## 2. 范围与投入建议

| 路线 | 自定主动工时估算 | 主要未知 | 决策 |
| --- | ---: | --- | --- |
| P0预检+一个钱包+主网付款+收据+材料 | 35–55小时 | SDK组合、钱包纯签名、用户测试和资格证据 | 主线 |
| XO Build增量 | 4–12小时，先2–4小时样例验证 | 版本/schema、用例独特性、个人真实反馈 | 过gate后做 |
| Migrate额外证据 | 2–5小时，视旧项目真实状态 | 功能对应、旧代码与旧demo | 不是新项目的捷径 |
| 成熟服务双向两跳桥 | 另12–24小时，另有链等待 | 地区、最小额、合约适配、流动性、失败恢复 | 只有P0稳定且仍有余量才做 |
| 双链自建HTLC/solver | 本次不估算成8天可审计产品 | 流动性与双链安全设计根本未闭环 | 删除 |
| 独立Media | 3–6小时以上，取决于媒介 | 内容独立价值、吸引力 | 不为1000 PUSD牺牲主线 |
| Avalanche x402/Team1 | 独立后续阶段 | 真正需求、facilitator与真实交付 | 比赛后再决策 |

这些是排期建议，不是官方标准或市场报价，熟练度和未知接口会影响实际工时。赛前准备也要真实计入投入；不要只统计比赛八天。

## 3. 现金成本模型

按用户已有工具优先，不默认采购新模型/服务。建议以**50–150美元新增现金的可选规划区间**作为早期讨论起点，实际支出以实时价格、最低转账额和用户确认预算为准；这不是已经授权的支出。已有订阅与个人时间另计。

| 项 | 预算处理方式 | 控制手段 |
| --- | --- | --- |
| 托管/域名/只读RPC | 先用现有或足够的基础方案，报价后确认新增 | 一个应用，一个必要持久存储；不订阅多家服务 |
| AI解释 | 默认关闭或限定测试调用，模型与价格运行时确认 | 不在资金关键路径，无模型也能演示 |
| 主网测试 | 资产本金、矿工费、承载资金分别列明 | 用户自有钱包、小额、明确上限、只测试必要路径 |
| 桥测试（若启用） | 两次兑换、最小额、滑点、第三方费单独核实 | 达不到预算或地区门槛则取消，不能挪用主线预算 |
| 数据存储 | 操作状态、最小收据与日志 | 不收集全钱包地址/xpub，不建大数据平台 |

本金转到另一个自有钱包不等于全部成为费用，但可能有不可用资金、报价风险和未回收承载额。不能把“交易费用很低”写成“项目无成本”。

## 4. 首期商业验证

主用户锁定BCH dApp开发者，商家付款是体验样例。先验证三个问题：

1. 对方是否实际需要从付款请求核验交易输出，而不是钱包现有确认页已足够？
2. 复用guard能否比自行编写校验更省集成/调试工作？最难接入的字段或功能是什么？
3. 对方愿意接入开源模块、提供测试反馈，还是愿意为托管诊断/支持付费？这些是不同强度信号。

收集一条影响产品决策的具体反馈优于若干泛泛好评。记录对方身份类型、观察任务、原话、授权展示范围、实际修改。没有外部答复时标未验证，不靠AI生成访谈。

可用替代品比较应实测具体钱包确认界面、开发者已有交易构建检查，不预设它们“没有安全功能”。本产品可能有价值的差异是应用层已确认意图与真实交易的可编程比较、跨UI复用和故障证据，而不是声称所有钱包都盲签。

## 5. 暂停与继续规则

| 情况 | 动作 |
| --- | --- |
| 失去准备直播资格且没有官方例外 | 清楚报告本届资格风险；不伪造参与证据；另评估开源交付价值 |
| SDK/钱包spike失败 | 先修最小兼容闭包，主线未形成前不增加UI包装或新赛道 |
| 赛期第3天仍不能可靠签名/控制广播 | 停止P1/P2，专注一个真实钱包闭环 |
| XO样例/用例无法证明 | 停止该bounty，不改写资金架构去迁就 |
| 桥地区/资金/双向流动性不满足 | 关闭桥，不用代理绕过限制、不用自己的热钱包替代 |
| 核心到11月20日才稳定 | 不再加功能，优先视频、slides、源码和资格证明 |
| 真实目标用户认为价值不清 | 改进一个具体检查/集成场景或文案；不堆链数和AI功能 |
| 未中奖但有人愿意集成 | 依据真实反馈评估后续，不把比赛名次当唯一需求信号 |

继续投入Avalanche的前提是：有明确使用方或生态贡献、对应代码/网络支付已经存在、预算和维护承诺可履行。Team1最高额度不是产品需求的证明。

## 6. 已选建议与重新打开条件

- D01：单应用优先。只有实际package复用或发布需求出现才拆monorepo。
- D02：确定性guard是唯一核心。AI只解释；用户验证显示输入理解是真问题时才加强提取。
- D03：普通支付不引入托管合约。未来有真实资金托管需求时单独立项，不作为本期修补。
- D04：一个真实钱包闭环为P0。第二钱包和深链在预算/期限允许时增加。
- D05：XO是可选可验证增量。官方工具与用例证明通过才纳入提交承诺。
- D06：Bridge/Media/Team1顺序后置。任何变更必须列出牺牲的主线任务，不凭“能多一个奖”直接展开。

这些是本包建议，由dot结合真实仓库与运行证据复核；不是已存在用户仓库中的不可修改历史决策。
