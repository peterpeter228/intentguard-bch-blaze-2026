# 02｜赛事规则、资格证据与提交验收

核查日期：**2026-10-27**。本章面向 BCH BLAZE 2026，时间统一用北京时间（Asia/Shanghai，UTC+8）。它说明规则与需要完成的动作，**不代表用户已经报名、点名、获准领奖或提交成功**。表内资格状态全部从“未完成”开始，dot 只有取得对应证据后才能更新。

## 一、参赛定位与范围

主线为 **IntentGuard BCH：支付意图预检 SDK → 用户钱包真实付款 → 可独立核验收据**。演示先用明确标注的恶意候选交易 fixture 展示阻止能力，再完成一笔真实 BCH 主网上的 PUSD 支付。普通退款请求属于 P1，由收款方自愿另行付款，不能描述成撤销原交易或保证退款。

本轮不自建双链资金托管桥。Stablecoin Bridge 和 Media 参赛后置，不为了增加报名项而牺牲主线完成度。XO Build 仅在官方真实 schema、debug tool 与最小交易 spike 通过后进入范围；Migrate 还须存在真实可工作的旧项目及可证明的功能迁移。此顺序是工程决策，不是官方指定产品形态。

公开规则允许全球开发者以个人或 2–4 人团队参赛；按这一公开口径，中国个人没有被赛事正文排除。但正文不能证明最终收款、KYC、税务或其他平台条件全部满足，不应写“保证中国个人无条件领奖”。[RULE1]

## 四、现行 Widget Factory 与首页披露

本次从官方 DoraHacks 获取并实际读取的模板为：[现行 Widget Factory 模板](https://docs.google.com/presentation/d/1Yfuk9CJkf4U9M_WukcELhumWgj3Ak6345Ewy8hSp-Hk/edit?usp=sharing)。不要沿用原方案其他 ID，也不要把模板示例中的虚构品牌、repo 或经营数字带入提交。[RULE1][RULE4]

该模板的七页依次为：品牌与团队；一句话功能及源码；项目起因；用户收益；BCH 使用方式；愿景与后续；结束。对应本项目，可填“付款请求可能与交易内容不同”“四种差异实际被阻止”“一次真实主网付款及收据”“可复用 SDK 与下一步集成”。未经访谈的市场需求、未经验证的客户数字必须标作假设。

首页顶部要链接**已填好的本项目短演示稿**，同时列源码及用于 EMBER2026 的 CashTokens 地址。旧项目再列旧 repo、新 repo、赛前旧 demo。地址应由用户掌控，使用库校验网络、类型和 Token-aware 能力，不以“字符串必须以 z 开头”替代完整解析。发布前在未登录会话检查演示稿和源码是否可供评委访问；需要授权时应提前解决实际访问问题，不能擅自把私有仓库公开。

## 五、赛前基线与赛期贡献

现在到正式开赛之间可以做规则研究、环境准备、能力探测和技术 spike，但**这些实际发生在赛前的工作须进入赛前基线**。不要通过改 commit 时间、删历史或换 repo 伪装原创。

dot 在开始正式实现前执行：确认是否确有 IntentGuard-402 或其他旧项目；记录旧 repo、固定 commit/tag、可运行步骤、旧演示 URL 与截屏；列清可复用组件、第三方来源和许可；给所有赛前 spike 标记日期。没有旧项目证据时按新项目计划，不申报已完成迁移。

开赛时冻结基线，并在 `delta.md` 为每项新增功能写明问题、实现 commit、对比说明、测试和演示入口。建议重点证明赛期完成的独立预检、钱包实际集成、签名前后的一致性验证、收据核验及用户体验改进。单纯改名、换配色、增加营销文案不应包装为显著改进。[RULE1]

若旧、新版本放同一仓库，保留可固定访问的旧版本与新版本入口，**并核对主办方是否接受这种形式**；官方正文要求旧/新 repo，不能自行断言一个 Git diff 已满足。

### XO 单独完成条件

模板须确实实现目标功能；提交真实执行使用的 invitation、对应链上交易、模板文件、debug tool 检视结果及复现步骤；合同结构适用时展示 follow-up action。迁移还要求原工作项目及新版入口。[RULE3]

约 500 词的开发反馈必须由本人书写，官方明确拒绝 AI 写作。dot 只整理客观日志、版本、错误及重现事实，不代写、改写或包装成“本人亲历”文本。需要翻译或语言辅助时，规则未明确允许，先核对主办方口径；没有实际反馈时状态仍为未完成。XO 是早期技术栈，spike 不通过就保留 WizardConnect 主线并放弃该附加项。[RULE3]

## 七、四项等权评分如何落到证据

官方三位评委对四类分别打 10 分，总分 120；换算后各占 **25%**。[RULE1] 不根据评委职位推测隐含权重，也不声称使用赞助组件必定加分。

| 评分项 | 本项目要证明什么 | 最小证据与验收 |
|---|---|---|
| 创新与创意 | 与已有钱包发送功能相比，独立核对外部支付意图和待签交易有新增价值 | `evidence/demo/adversarial-cases.md`：收款人被换、伪同名category、未授权输出/错误找零、超限费用四类候选被明确阻止；均标注受控fixture |
| 设计与可用性 | 评委很快能理解并使用，签名前知道付款给谁、付什么、多少 | `evidence/ui/judge-walkthrough.md`：无钱包可看示例；需要真实付款时再连接；录制正常、拒签及恢复路径；手机不遮挡关键字段 |
| 技术实力 | 拦截来自确定性核验，真实支付与收据可重验 | `evidence/validation/summary.md`：预检冻结快照与签名后交易一致；金额/Token/费用校验；区分签名、广播、确认；收据独立验证，错误时拒绝显示成功 |
| 商业/投资潜力 | 明确谁会集成、问题多频繁、为何值得使用 | `evidence/product/validation.md`：用户假设、现有替代、SDK集成示例；如已获授权并完成访谈则保存真实反馈，否则明确未验证 |

以上是本项目验收设计，不是主办方额外硬性规则。四类恶意测试只在本地受控候选中展示，不能向真实他人发起攻击。若 SDK 没独立读取交易内容，只相信自己生成的“安全”标签，不能声称已经验证了支付安全。普通收据也不是官方认证或保证资产价值。

## 八、知识产权与最后的人类动作

官方 bounty 总则存在提交即放弃项目知识产权或类似权利的宽泛表述。[RULE3] 本章不把它解释成某一确定法律后果，也不把“代码开源”当成自动解决。正式 bounty 提交前，应把条款原文、适用的提交范围、本人旧资产、新增代码、第三方许可与未澄清问题记录在 `evidence/submission/rights-review.md`；如其范围会影响用户保留旧项目权利，应取得主办方澄清后再决定。准备代码和申请材料不代表已经替用户接受条款。

需集中交给人的事项：真实报名与团队信息；准备直播现场点名；Telegram真实确认；提供本人控制的钱包地址；主网交易签名；本人完成XO反馈；阅读实际提交条款；最终提交及可能的领奖身份材料。本文不授权 dot 发消息、签名、转账、接受条款或提交申请；后续用户明确授权的事项按当时授权继续，无须为同一动作重复询问。

dot 应自主完成未被这些动作阻塞的研究、开发、浏览器实测、材料整理和证据核验。遇到缺少人工证据，标出准确缺口并继续独立工作，不把整个开发停在反复确认上。
