# 产品需求：IntentGuard BCH

## 1. 产品承诺

**用户说要付什么，实际交易就只能付被确认的内容。** IntentGuard BCH 在本应用构建和签名流程内，把结构化付款意图与真实 BCH 交易逐项比对，并把付款结果做成可重复验证的证据。

它是应用集成的交易检查器及演示收款流程，不是浏览器全局钱包防护器，不保证阻止其他 dApp 绕过它，不证明商品交付或交易对手信誉。使用者仍需确认收款人的身份。本产品不凭地址“看起来合法”宣称商家可信。

### 目标用户

| 用户 | 场景 | 本期收益 |
| --- | --- | --- |
| BCH dApp 开发者 | 构建支付、让钱包签名之前 | 复用一次可审计的意图/交易检查，减少错账与错误提示 |
| 接收 BCH/PUSD 的小商家、内容或 API 提供者 | 给客户发送具体付款请求 | 请求内容、交易结果和收据可对应，不靠聊天截图确认 |
| 使用外部 AI/代理生成付款请求的人 | AI 建议付款但不应自行决定资金 | 将提取结果变为待确认草稿，最终资金条件由规则约束 |

首期主用户是正在接入 BCH/CashTokens 支付的 dApp 开发者，降低资金字段校验和故障诊断成本；商家付款用于展示业务效果，AI是外部候选来源。托管收据收费仍是待验证假设。以上是待验证的用户假设，不代表已有客户。首轮访谈目标为 3 名相关用户或开发者，记录原话、任务和观察，不把测试者数量写作付费客户。

## 2. 参赛定位

官方四项评分等权；我们的设计推导如下。[S01]

| 评分方向 | 本产品的可见证据 | 不足与处理 |
| --- | --- | --- |
| 创新 | 同一付款请求遇到被篡改交易时，独立预检可定位差异；第三方 demo 调用同一 guard | 单纯钱包转账不新颖；必须演示外部候选与独立核验 |
| 设计 | 无钱包即可打开攻击检查示例和既有真实收据，正常支付只保留必要步骤 | 不让评委先充值或注册才看到价值 |
| 技术 | 逐输出验证、CashTokens/NFT 保护、HD 路径、签名后二次验证、真实主网证据 | 不用复杂托管协议来堆技术量 |
| 商业 | 明确一个集成者类型，提供可复制的 SDK 接入示例、真实访谈与成本模型 | 付费意愿未证实；不得声称已盈利 |

## 3. 唯一主线与优先级

### P0：必须交付

1. **付款请求**：创建或载入一个明确资产、金额、网络和收款地址的请求；任何 AI 提取都停留在未确认草稿。
2. **用户确认意图**：显示完整地址、资产 category、金额、BCH 承载资金及费用上限。用户能打开细节并修改错误。
3. **独立交易预检**：从链上读 prevouts，对实际交易输入输出做确定性校验。处理收款地址替换、假同名币、超额付款、错误找零、费用异常、未支持资产等。
4. **用户钱包支付**：WizardConnect；P0完成一套明确钱包版本、设备与浏览器组合，第二钱包和手机深链属于P1。手机视口UI验收不等同手机钱包实测。所有签名由钱包完成。
5. **签名后复核与广播**：确认返回交易仍满足已批准意图；本应用控制的广播以 `broadcast:false` 能力验证为前提。签名、广播、确认状态分别展示。
6. **独立收据**：以链上实际输出为依据生成结构化记录，任何人可用公开链数据重查。收据同时标示自付演示、确认数和核验时间。
7. **评委体验**：首屏能点“查看防篡改示例”和“查看已核验主网收据”，不要求钱包；真实支付入口独立且显式标明网络和金额。
8. **可复用接口**：提供一个与 UI 解耦的 TypeScript guard 模块、稳定报告结构和独立调用示例。npm 发布不是本期必要条件。
9. **参赛交付**：首页规则链接、真实旧版披露（如适用）、七页短演示、视频、源码、复现步骤和证据索引。

### P1：在 P0 稳定后选做

- XO 模板实现同一可解释付款需求，通过官方 schema、Debug Tool 和真实链上交易验证。
- 已有核心功能的 XO 迁移；新项目不申报 Migrate。
- 接收人自愿退款请求、退款交易核验；不能标为撤销原付款或必定退款。
- 第二个钱包、手机深链或移动二维码优化；必须如实标记已测/未测组合。
- 可选 AI 文本请求提取与结果解释。若模型不可用，结构化表单与检查流程完整可用。

### P2：单独决策

成熟供应商组合的双向跨链路线、Avalanche 标准 x402 端点、Team1 申请、独立 Media 作品。详见第 07 章，不默认同时开发。

### 本期排除

自写 HTLC/资金池、自动持私钥 Solver、NFT 收据铸造、多链自动轮询平台、微服务拆分、复杂登录/多租户计费、为每次预检先付 x402 费用、动态 AI 配音漫画、无依据的安全评分百分数。

## 4. 主要用户旅程

### 旅程 A：评委 60 秒理解产品

打开首页 → 看到一句话价值 → 点“运行防篡改示例” → 原请求是付 1.00 PUSD 给收款人 A → 候选交易把收款脚本换成 B → 红色报告说明差异与被阻止的步骤 → 切换正常候选 → 通过检查 → 打开已存在的真实主网收据。

攻击候选使用**标明为本地测试数据的样例**，不向钱包请求签名、不广播，也不伪装真实发生过的攻击。真实主网收据与攻击 fixture 分开标识。

### 旅程 B：用户实际付款

打开付款请求 → 确认商家与金额 → 连接钱包 → 获取相关分支余额和 UTXO → 构建并预检 → 看“你将支付”的摘要 → 钱包签名 → 复核返回交易 → 广播 → 显示 txid 和当前确认状态 → 查看或导出收据。

相同请求重复点击不能生成并行签名流程。网络不确定时显示“正在核对原交易”，先查原 txid，而不是让用户再付一次。

### 旅程 C：开发者集成

打开 `/developers` → 阅读输入契约、支持范围与错误码 → 在独立示例项目调用 `verifyCandidate()` → 得到与网页一致的报告 → 运行一组篡改测试 → 了解如何在自己 dApp 的签名前、签名后两处调用。

函数名是本项目拟定义的内部契约，不是第三方 SDK 的既有 API；具体以实现后的 types 为准。

## 5. 页面和信息层级

| 页面 | 主要信息 | 主要操作 | 必备异常反馈 |
| --- | --- | --- | --- |
| `/` | 一句话价值、演示入口、参赛链接 | 查看预检示例/真实收据 | 没有真实证据时不显示绿色成功案例 |
| `/pay/[id]` | 请求来源、完整金额与资产、收款人、网络 | 确认→连接→预检→签名 | 地址错误、过期、余额不足、网络错、钱包拒签 |
| `/inspect` | 已确认意图与候选差异 | 载入安全样例/攻击样例 | 未知脚本/缺失 prevout 标为不能核验 |
| `/receipt/[id]` | txid、输出索引、资产与数量、确认数 | 重新核验、区块浏览器、下载 JSON | 链离线、交易未见、冲突、重组、过期快照 |
| `/developers` | guard 输入输出与支持范围 | 查看例子/运行步骤 | 版本不匹配明确报错 |
| `/about` 或首屏折叠区 | 开源许可、贡献、版本和真实边界 | 源码、演示稿、旧版链接 | 不允许占位 URL 对外上线 |

参赛演示默认英文；中文可作为后续本地化。金额和地址视觉优先；状态除了颜色还要有文本。按钮文案用结果导向语言。主页面不显示内部包名、模型名、调试序号或“零知识安全”等与用户决策无关的词。

主按钮附近显示“主网/测试网”和费用，钱包确认前再次显示。支持桌面 1366×768、手机 390×844；长地址换行、复制后给反馈，二维码不能被浮层遮挡。网络慢时说明等待原因，不无限转圈。

## 6. Guard 的功能承诺

| 检查 | 通过条件 | 失败行为 |
| --- | --- | --- |
| 网络 | 请求、钱包会话、provider、资产 registry 一致 | 阻止构建与签名 |
| 资产 | 精确 category 匹配且元数据来自已核实 registry | 不按 symbol 接受同名币 |
| 金额 | 每个允许收款输出总额符合意图；无额外泄漏 | 阻止签名；显示差值 |
| 收款人 | 锁定脚本与用户确认地址解码结果一致 | 阻止签名；不靠字符串缩写比较 |
| 找零 | 来自钱包许可分支、路径有证据、数量守恒 | 不允许服务端任意给出“找零地址” |
| 原生 BCH | 承载输出、转账、手续费全计入总流出 | 超出已批准上限时阻止 |
| NFT | P0 输入不含 NFT | 排除并解释；不能烧掉 NFT |
| 费用 | 按实际体积估算、上限和已确认成本约束 | 无数据不能假装固定650 sats即可 |
| 数据可靠性 | 前序输出和最新状态可核验 | 输出 UNKNOWN/UNSUPPORTED，不能 PASS |
| 签名后变化 | 非签名字节和授权范围仍与批准内容匹配 | 不广播；记录可解释错误 |

“PASS”仅表示在声明支持范围和观察到的链数据下，交易符合该意图。不是合约审计证明，也不是抗所有恶意浏览器、扩展、钱包或后台攻击的保证。

## 7. 收据与退款语义

收据至少包括：网络、txid、资产 category、十进制显示金额及整数金额、收款脚本/地址、实际输出索引、确认数、观察时间、区块哈希（如已确认）、核验器版本、可复核来源、演示标识。请求 ID 与应用意图 hash 只是应用层关联，不能伪称链上原生发票证明。

若需要可在交易中核实请求关联，可以在后续版本评估标准数据输出承诺；P0 不为了“收据”新增代币或复杂合约。没有链上承诺时，页面明确“交易事实已核验，订单关联由本应用记录”。

退款 P1 只把付款收据与另一笔接收人主动返款关联。收款人未签名、未返款时显示“已请求/待处理”；核验返款交易后才显示“返款已观察/已确认”。不能承诺点按钮就恢复原 UTXO 或回滚跨链过程。

## 8. 商业验证与产品指标

开发验收目标（自定，不是官方成绩门槛）：首次访客不连接钱包也能在 60 秒内看懂一个阻止错付的例子；正常流程没有多余登录；用户取消能恢复；每个演示结论能追到具体交易或 fixture。

记录：5 次受控测试的完成率/失败原因/耗时，至少 3 条相关开发者或商户反馈，以及一条“愿不愿意把此模块接入自己流程”的明确答复。若没有取得外部回复，提交如实标记“尚未验证”，不能补写。

潜在收入假设：基础验证库开源；未来按团队收取托管收据、错误分析或集成支持费用。此期不做收费系统，不声称收益来自交易量，不靠未经验证的跨链手续费预测估值。

## 9. 验收终点

P0 完成须同时有：受支持版本的可复现构建、核心篡改负例、至少一条真实钱包主网支付链路、签名后复核、可重查收据、真实浏览器点击证据、匿名可访问演示、规则矩阵和真实时间线。缺任一关键项不以“基本完成”代替说明。

失败时缩减顺序：不启动桥、Media与Team1开发 → 去掉退款和第二钱包 → 暂停未通过门槛的XO → 关闭可选AI提取；保留核心预检、真实主网付款和收据。若主网付款本身无法实现，立即报告参赛资格风险，不能用 Chipnet 截图冒充主网。
